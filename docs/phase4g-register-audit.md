# Phase 4G — read-only audit: can the M7 verifier's 252 registers be reduced?

**Gate verdict: FAIL. No credible ≥16-register release exists within the current Triton
implementation.** So no kernel code experiment is opened, per the review's instruction.

## The structural fact this audit exists to address

Phase 4C established, from `ptxas` on the production kernel:

```
252 registers/thread, 0 bytes spill, 57,344 B shared, 4 warps
=> 2 resident CTAs/SM (65,536 / (252 x 128) = 2), only 1,024 registers of headroom per SM
```

Any verifier optimisation that **adds** per-thread state is therefore infeasible. Future
verifier work must **free registers first**. This audit asks whether that is realistic.

## Method (compile-only, no GPU execution, no production change)

Structural variants are generated by verified textual deletion from the production source
(each anchor must match exactly once or the generator fails), then compiled and measured with
`ptxas -v`. The variants are **deliberately incomplete** — they compute fewer query rows —
because the question is what each part *costs*, not whether the variant is correct.

## Result

| variant | rows | registers | spill (stores/loads) | shared |
| --- | --- | --- | --- | --- |
| production | 48 (32+16) | **252** | 0 / 0 | 57,344 B |
| drop the 16-row group | 32 | **168** | 0 / 0 | 49,152 B |
| drop the 32-row group | 16 | **128** | **16 / 8** | 40,960 B |

Marginal cost:

| step | registers | per row |
| --- | --- | --- |
| 16 → 32 rows | +40 | **2.5/row** |
| 32 → 48 rows | +84 | **5.25/row** |

**Register cost is superlinear in live rows**: the allocator has slack at 16–32 rows and is
squeezed at 48, where each additional 16 rows costs more than twice as much. That is the
signature of a kernel already at the register limit, consistent with the 0-byte spill at 252.

Note also that the 16-row variant **still spills** (16 B / 8 B) at 128 registers — the
remaining row group plus the loop's addressing and K/V decode temporaries do not fit
comfortably even alone, which further indicates there is no slack anywhere to reclaim.

## Why the obvious levers are all closed

| lever | verdict |
| --- | --- |
| **Remove padded rows** | Not available. 48 rows = `qmax` 8 x GQA 6, all *useful* rows, not padding. With q=8 every row is needed. |
| **Split rows across CTAs** | Explicitly ruled out by the project's own design constraint: it duplicates the dominant long-context K/V traffic. |
| **Re-load Q per tile instead of holding it** | Q is `qs0`+`qs1` = 48 rows x 256 dim bf16 = 24 KB per CTA, live for the whole scan. Re-loading per tile from **global** would add 24 KB per tile x up to 7,812 tiles at 250K — a new global-memory pass. The gate forbids it. |
| **Stage Q in shared memory and re-read per tile** | The only structurally sound lever: it would free ~48 registers for ~24 KB of smem per CTA. But smem is already 57,344 B/CTA with 2 CTAs/SM = 114,688 B of 164 KB available; adding 24 KB x 2 CTAs = 48 KB puts it at **162 KB, at the limit**. And Triton exposes no direct smem staging control for this pattern, so it requires a **hand-written CUDA kernel** — a rewrite, not a tuning experiment, and outside this phase's scope. |
| **Process row groups sequentially to shorten softmax-temporary live ranges** | The source already computes group 0's `s/p/acc` and then group 1's sequentially, so Triton's allocator already sees non-overlapping live ranges; there is no obvious redundancy left. |
| **Register tuning / maxnreg** | Not attempted and not attempted-able: with 0 spill and only 1,024 registers of headroom, forcing a lower cap would spill into local memory, which is a new memory pass. |

## Relationship to prior negatives (checked to avoid repeating E21–E42)

- **E33/E36** (D256 register accumulator hitting 255 regs + spill): this audit **explains**
  those results — the kernel is genuinely at the register ceiling and adding accumulator state
  is impossible. Phase 4C reproduced the arithmetic (+48 regs → 300 > 255).
- **E37 / isolated cp.async-K**: not re-attempted. The audit found no register interaction that
  would change that result.
- The audit did **not** go looking for new Sage-style micro-optimisations; the question was
  narrowly whether registers can be freed.

## Conclusion and what it means for the next round

**There is no ≥16-register release available inside the current Triton kernel.** Freeing
registers requires either (a) hand-written shared-memory staging of Q — a kernel rewrite that
lands at the shared-memory limit, or (b) a different decomposition of the query rows that
avoids duplicating K/V traffic. Neither is a tuning change.

So the honest position for future verifier research is:

> The M7 verifier is at 252/255 registers with zero spill and exactly 2 resident CTAs/SM. Any
> optimisation that adds per-thread state is blocked, and the cheap ways to *remove* state are
> also blocked. Verifier work therefore requires a **structural rewrite** (hand-written kernel
> with explicit shared-memory staging), not an incremental experiment — which is a decision to
> make on its own merits, with the whole-step payoff still ~1.5% for a 3% verifier win (Phase 2
> gives the verifier 52.2% of the 250K step).

That last figure is why this is a "do not start" rather than a "start with care": the ceiling on
an incremental verifier win is small, and the register audit says incremental is not even
available.
